# Delivery Implementation Plan (Plan 5)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make `docker compose up` produce a working system, prove all nine walkthrough steps against it, and leave a reviewer everything they need to judge the work.

**Architecture:** Two multi-stage images and one Compose file. Postgres carries a healthcheck because a started container is not an accepting one. The backend applies both modules' migrations at startup, so a reviewer runs one command and nothing else. CI mirrors the same commands the developer runs, with the Docker-dependent jobs separated from the fast ones.

**Tech Stack:** Docker Compose, multi-stage Dockerfiles (`dotnet publish`, Next.js `output: 'standalone'`), GitHub Actions, `Microsoft.AspNetCore.RateLimiting`.

**Spec:** `context/architecture.md` 10.1 (the stack), 10.2 (the CI jobs), 7.4 (rate limiting), 7.5 (the dashboard), 8.1 (the definition of done); assessment lines 373-380 (deliverables) and 487-494 (submission)

**Rubric reach:** The CI/CD bonus (+3) and the rate limiting bonus (+2). More importantly it closes the definition of done in 8.1, which is the half of "done" that no amount of unit testing can supply — and it produces deliverables 5 and 6, which are graded and currently absent.

## Global Constraints

- Every `dotnet` command prefixed:
  ```bash
  PATH="/opt/homebrew/opt/dotnet@9/bin:$PATH" dotnet …
  ```
- **A reviewer needs `docker compose up` and nothing else** (NFR-7): no credentials, no accounts, no manual migration step
- **No mail container** (D-08). See task 0
- Test-driven where there is behaviour to test. Compose files and Dockerfiles are configuration, exempt under architecture 8.3 — but each is *verified by running it*, which is the second of 8.3's two conditions and is stricter here than a test would be
- Warnings are errors. Everything green before any commit
- **The smoke run is the acceptance criterion, not a formality.** If it fails, the fix is the system, not the test

- [ ] **Step 2: Write `backend/Dockerfile`**

```dockerfile
# Restore before copying the rest, so a source edit does not re-download every
# package. The project files are what invalidate a restore; the code is not.
FROM mcr.microsoft.com/dotnet/sdk:9.0-alpine AS build
WORKDIR /src

COPY Directory.Build.props Directory.Packages.props global.json JobTracker.sln ./
COPY src/ ./src/
RUN dotnet restore JobTracker.sln

RUN dotnet publish src/Api/JobTracker.Api/JobTracker.Api.csproj \
    -c Release -o /app --no-restore

FROM mcr.microsoft.com/dotnet/aspnet:9.0-alpine AS runtime
WORKDIR /app

# Not root. A container that never needs to write to its own filesystem should
# not be able to.
RUN adduser --disabled-password --no-create-home --uid 64198 app
USER app

COPY --from=build /app .
EXPOSE 8080
ENTRYPOINT ["dotnet", "JobTracker.Api.dll"]
```

The restore copies `src/` rather than each `.csproj` individually. The finer-grained version caches better and needs one `COPY` line per project — eleven of them, each a line that goes stale when a project moves. State the trade rather than pretending the coarse one is optimal.

- [ ] **Step 3: Write `frontend/Dockerfile`**

```dockerfile
FROM node:22-alpine AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci

FROM node:22-alpine AS build
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
# Absent at build time on purpose: the container gets it from Compose, so one
# image serves both the in-memory demo and the real stack.
RUN npm run build

FROM node:22-alpine AS runtime
WORKDIR /app
ENV NODE_ENV=production
RUN addgroup -g 1001 nodejs && adduser -u 1001 -G nodejs -D nextjs
USER nextjs

COPY --from=build --chown=nextjs:nodejs /app/.next/standalone ./
COPY --from=build --chown=nextjs:nodejs /app/.next/static ./.next/static
COPY --from=build --chown=nextjs:nodejs /app/public ./public

EXPOSE 3000
ENV HOSTNAME=0.0.0.0
CMD ["node", "server.js"]
```

`HOSTNAME=0.0.0.0` is not decoration: the standalone server binds localhost by default, and a container that binds localhost is a container nothing can reach.

- [ ] **Step 4: Write both `.dockerignore` files**

Backend excludes `bin/`, `obj/`, `tests/`. Frontend excludes `node_modules`, `.next`, `coverage`, `test-results`, `playwright-report`. Without them the build context carries hundreds of megabytes of artefacts that the build then discards.

- [ ] **Step 5: Build both, and time them**

Both must build. Record the sizes — an image nobody measured is an image nobody knows the cost of.

- [ ] **Step 2: Write `DatabaseMigrator`**

```csharp
/// <summary>
/// One command and nothing else (NFR-7). Each module migrates its own context
/// into its own schema with its own history table; adding a module is adding a
/// line here.
///
/// It runs before the host serves a request, so a reviewer never sees a 500
/// caused by a table that does not exist yet.
/// </summary>
internal sealed class DatabaseMigrator(IServiceProvider services, ILogger<DatabaseMigrator> logger)
{
    public async Task MigrateAsync(CancellationToken cancellationToken)
    {
        await Migrate<JobsDbContext>(cancellationToken);
        await Migrate<BillingDbContext>(cancellationToken);
    }
    …
}
```

Guarded so it runs only when configuration asks for it: a test host that migrated on every start would fight the fixture.

- [ ] **Step 3: Write `docker-compose.yml`**

```yaml
services:
  postgres:
    image: postgres:17-alpine
    environment:
      POSTGRES_DB: jobtracker
      POSTGRES_USER: jobtracker
      POSTGRES_PASSWORD: jobtracker
    volumes:
      - postgres-data:/var/lib/postgresql/data
    healthcheck:
      # A started container is not an accepting one, and migrations against a
      # database still recovering fail in a way that looks like a code fault.
      test: ["CMD-SHELL", "pg_isready -U jobtracker -d jobtracker"]
      interval: 2s
      timeout: 3s
      retries: 30

  backend:
    build: ./backend
    depends_on:
      postgres:
        condition: service_healthy
    environment:
      ASPNETCORE_ENVIRONMENT: Development
      ASPNETCORE_URLS: http://+:8080
      ConnectionStrings__Database: Host=postgres;Port=5432;Database=jobtracker;Username=jobtracker;Password=jobtracker
      # Committed on purpose: it signs tokens for a local database of fictional
      # rosters. A deployed environment supplies its own and appsettings.json
      # carries none, so a missing key fails loudly instead of falling back.
      Jwt__Key: compose-development-signing-key-at-least-32-bytes
      Database__MigrateOnStartup: "true"
    ports: ["8080:8080"]
    healthcheck:
      test: ["CMD-SHELL", "wget -q -O- http://localhost:8080/health || exit 1"]
      …

  frontend:
    build: ./frontend
    depends_on:
      backend:
        condition: service_healthy
    environment:
      JOBTRACKER_API_URL: http://backend:8080
    ports: ["3000:3000"]

  postgres-data:
```

The frontend waits for `service_healthy` rather than `service_started`, which architecture 10.1 does not require — but a frontend that starts against a backend still migrating renders an error page on the first load, and that is the first thing a reviewer sees.

A `/health` endpoint has to exist for that healthcheck. Add it, anonymous, in task 3 alongside the rate limiter so both changes to the pipeline land together.

### Task 4: The Hangfire dashboard, closed by default

**Files:**
- Create: `Api/Authentication/LocalOnlyDashboardFilter.cs`
- Modify: `Program.cs`
- Create: tests in `Api/DashboardTests.cs`

This is the item plan 4 left open, stated there rather than discovered here.

The dashboard is wanted — architecture 7.5 exposes it so the async pipeline is inspectable without reading logs. The problem is that it cannot use bearer authentication: a browser navigating to `/hangfire` sends no `Authorization` header, so the fallback policy would refuse every request and the feature would be dead rather than protected.

Three options. **Development-only** is where it already is, and it is not enough on its own: `ASPNETCORE_ENVIRONMENT` is a string in a Compose file, and the failure mode is silent. **Basic auth** adds a credential to invent, document and leak. **Local-only** refuses any request whose remote address is not loopback, which is exactly the reviewer's case (`docker compose exec` or a published port from the host) and no one else's.

Take local-only *and* keep Development-only. Two conditions, both cheap, and neither depends on the other being right.


### Task 5: The nine steps, against the stack

**Files:**
- Create: `frontend/e2e/smoke.spec.ts`
- Modify: `frontend/playwright.config.ts`, `frontend/package.json`

**Interfaces:**
- Consumes: the running Compose stack
- Produces: the executable form of the definition of done (architecture 8.1)

Steps 4 and 9 are already proven over HTTP in the backend suite, so this should be a confirmation. If it is not, the difference is infrastructure — networking, environment, startup order — and that is precisely what this test exists to catch.

- [ ] **Step 1: Add a Playwright project that does not start its own server**

The existing `webServer` builds and serves the in-memory app. The smoke run targets a stack that is already up, so it needs a second project with `webServer` absent and `baseURL` from the environment. Two configs would drift; one config with two projects will not.

```bash
npm run test:e2e            # in-memory, unchanged, 7 tests
npm run test:smoke          # against Compose
```

- [ ] **Step 2: Write the smoke spec**

All nine steps in one test, because they are one story and a reviewer reads it as one:

```ts
test('the nine steps of the acceptance walkthrough', async ({ page }) => {
  // 1. Open the job list
  // 2. Create a job through the form
  // 3. It appears as Scheduled
  // 4. The assignee is notified            -> queried from Postgres
  // 5. Narrow by status and find it
  // 6. Record that the crew started
  // 7. Complete with signature and photos
  // 8. It shows Completed
  // 9. An invoice exists and the customer was notified  -> queried from Postgres
});
```

Steps 4 and 9 query the database, because neither consequence appears in the interface — design A5 step 6 says completion does not claim they happened. Reading the database the system just wrote is the normal shape of an integration test (architecture 8.1); the alternative, a diagnostics endpoint, adds public surface D-04 declined to give Billing.

- [ ] **Step 3: Poll with a bound rather than sleeping**

`NFR-4` promises the consequences arrive *within seconds*, not immediately. A bounded poll asserts on eventual consistency; a fixed sleep pretends the system is synchronous and fails on a slow machine for a reason that is not a defect.

- [ ] **Step 4: Run it against the real stack**

```bash
docker compose up --build --wait
npm --prefix frontend run test:smoke
docker compose down -v
```

**This is the definition of done.** It either passes or the work is not finished.

## Self-Review

**Spec coverage.** Architecture 10.1's three services and its healthcheck condition: task 2. 10.2's six jobs: task 6. 7.4's sliding window partitioned by tenant with `Retry-After`: task 3. 7.5's dashboard: task 4. 8.1's definition of done: task 5. Assessment deliverable 5 (architecture diagram) exists in `docs/design-principles.md` §1 and the README links it; deliverable 6 is task 7.

**Section 5's remaining rubric points are what this plan is worth.** Everything else is bonus (+5) and presentation. But presentation is graded, and a reviewer who cannot start the system scores what they can see.

**The riskiest task is 2, and not for the obvious reason.** The images will build; the failure I expect is the frontend's server-side `fetch` reaching `http://backend:8080` from inside the network while the browser reaches `localhost:3000`. That asymmetry is invisible on a developer's machine, where both are localhost, and it is exactly what a Compose smoke run exists to find. If it bites, the fix is that server-side code uses the service name and nothing client-side calls the API directly — which is already true by design (D-29 put every read behind a Route Handler), and task 5 is what proves it.

**One thing I will not do.** I will not weaken the smoke test to make it pass. If step 4 or step 9 fails against Compose, the pipeline is broken in a way the in-process tests could not see, and that is a finding worth more than a green run.

**What this plan does not deliver.** OpenTelemetry (+2), Lighthouse evidence (+2) and screen-reader testing (+1) are bonus criteria this plan skips. They are named here so the omission is a decision rather than an oversight: each needs infrastructure or a manual pass that the remaining scope does not justify, and D-15 already declined tracing.
